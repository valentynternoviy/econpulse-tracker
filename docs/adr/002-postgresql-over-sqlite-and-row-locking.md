# ADR-002. PostgreSQL та песимістичне блокування рядка позиції (`SELECT ... FOR UPDATE`) для угод портфеля

Статус: прийнято, 2026-11-23

## Контекст
Ключова операція системи — реєстрація угоди купівлі/продажу (`Trade`) із перерахунком позиції портфеля (`Position`). Згідно з ТЗ: кількість у позиції ніколи не може стати від'ємною (продаж понад залишок повертає `422`), повторне надсилання з тим самим `idempotency_key` не створює дубль, а за одночасного надходження двох конкуруючих продажів однієї позиції успішним має стати лише той, для якого вистачає залишку.

## Розглянуті варіанти
1) SQLite як основна СУБД — простіше локальне розгортання без окремого контейнера, але SQLite блокує всю базу на запис і не підтримує рядкового блокування `SELECT ... FOR UPDATE` та повноцінного аналізу планів `EXPLAIN ANALYZE` у продукційному багатокористувацькому режимі.
2) PostgreSQL із транзакційним блокуванням рядка `Position` (`SELECT ... FOR UPDATE`) та унікальним обмеженням `(user_id, idempotency_key)` на таблиці `trades` — забезпечує атомарність, чесну серіалізацію конкуруючих продажів одного користувача без блокування інших користувачів, і багаті можливості аналітичних запитів (`percentile_cont`, `date_trunc`).

## Рішення
Використовувати PostgreSQL 16 як основну СУБД із транзакційним блокуванням рядка `positions` (`FOR UPDATE`) та унікальним індексом `(user_id, idempotency_key)` у таблиці `trades`. Для швидких локальних/CI-тестів підтримувати сумісність міграцій і SQLAlchemy 2.0 з `aiosqlite` (із fallback на транзакційну серіалізацію).

## Наслідки
Позитивні:
- виключається стан гонитви (race condition) при одночасних продажах однієї позиції;
- ідемпотентність гарантується на рівні обмеження цілісності СУБД, а не лише перевіркою в пам'яті;
- серверна агрегація історії (мінімум, максимум, середнє, медіана) виконується нативно в базі даних.

Негативні:
- потрібен окремий контейнер PostgreSQL у `docker-compose.yml` та керована БД для хмарного розгортання;
- у разі високої конкуренції на один і той самий рядок позиції конкуруючі транзакції очікують зняття блокування (для персонального портфеля це очікувана та бажана поведінка).

## Умова перегляду
Якщо система перейде на високочастотну торгівлю з тисячами угод за секунду на один акаунт, коли знадобиться event sourcing або оптимістичне версіювання з чергою.
